# 云同步（跨设备加密同步）设计草案

> 状态：**草案第二版，尚未实现**。已定的决定和仍待确认的事项见第 17 节，实现前要先完成第 16 节的实测。
>
> 命名：网站里的“同步”已经指“从鹰角拉取记录”，所以这个功能叫 **云同步**，避免混淆。

## 1. 核心思想

- **UID 默认就是公开的数字。单靠 UID 拿不到任何数据，连密文也拿不到。**
- **密码模式**（推荐）：所有权靠**密码的加盐散列**证明。
  - 读写只需要 UID + 密码，不需要鹰角 token。
  - 核对通过之前什么都不给，所以外人只能在线猜密码，速度由 Worker 按账号限死（7.5）。
  - 派生过程中有一步只有服务器能算、但服务器看不到密码（OPRF，7.2）：任何一样东西单独泄露，都不能拿来离线猜密码。
  - 盐由 UID 算出来，用户不用自己同步盐，盐也不用去服务器转一圈。
- **无密码模式**（不推荐）：所有权靠**中央服务器验证**。
  - **每一次**云同步 API 请求都必须带上有效的鹰角 token，由 Worker 当场向鹰角核实。
- **Worker 永远不相信客户端发来的数据。**验证全部在 Worker 里完成，通过之后才授权、才返回数据（第 4 节）。

## 2. 目标与边界

目标：

- 同一个游戏账号（游戏 + UID）的记录，在多个浏览器、多台设备之间合并。
- 服务器（Cloudflare Worker + Durable Object）只存密文。
- 本地仍然是主副本：云端出问题、忘记密码，都不影响本地数据。
- 尽量不需要升级 Cloudflare 付费版：数据密度尽量高，请求和写入尽量少（第 9、12 节）。

不做的事：

- 不上传任何鹰角 token（账号 token、OAuth token、u8 token、角色 token 都不进云端）。
- 不同步本机设置：统计同意、反馈编号、快照、界面偏好。
- 不建立用户名、邮箱一类的账号体系。
- 密码模式不提供密码找回。忘记密码只能用最全的浏览器覆盖云端（第 7.10 节）。

## 3. 设计前提（三个事实）

1. **UID 不是秘密。**
   - 游戏里能看到，分享图上也有，而且只有 9～10 位数字。对 UID 做哈希，几秒钟就能穷举反推回来。
   - 所以 UID 的哈希只能当“不直接写出 UID”的假名用，不能当秘密，更不能当加密密钥的来源。
2. **鹰角账号里没有“稳定、并且只有用户自己知道”的值。**
   - token 会失效、会变；UID、hgId 都不是秘密；鹰角接口的响应本来就经过我们的转发 Worker。
   - 所以只靠鹰角账号派生出来的密钥，服务器一定也算得出来。
   - 无密码模式的保密性因此只能依靠服务器不作恶。这是它“不推荐”的根本原因（第 8 节）。
3. **每条记录都有幂等键**（寻访的 `key`、源石/充值的 `kind + key`）。
   - 合并就是取并集，重复合并没有副作用。
   - 所以云同步不需要处理冲突，也不需要加锁。
   - 合并逻辑直接复用导入文件的那一套（`importExportFile`）。

## 4. 原则：Worker 不信任客户端

Worker 把收到的一切都当作不可信的输入。能不能读数据、能不能写入、能不能删除，只取决于 **Worker 自己验证过的东西**，从不取决于客户端“声称”的内容。

### 4.1 每个输入怎么验证

| 客户端发来的 | Worker 怎么处理 |
|---|---|
| `game` | 白名单（`arknights` / `endfield`），其他值直接拒绝 |
| `uid` | 只出现在需要鹰角证明的请求里，只用来指明“要证明哪个角色”。Worker 必须在鹰角返回的绑定列表里找到它，否则 403；之后用的是鹰角响应里的 uid |
| `locator` | 需要鹰角证明的请求：忽略客户端传的值，由 Worker 用核实过的 uid 自己计算。密码模式：只当查找键用，授权完全取决于 `authKey` 能否核对通过 |
| `authKey` | 和存储的 `verifier` 做常量时间比较 |
| 鹰角 token | Worker 自己调用鹰角接口核实（第 8.2 节），任何异常都按失败处理 |
| 密文 | 密码模式下 Worker 解不开，只检查信封格式、大小和配额。内容是否完整由浏览器用 AES-GCM 校验 |
| `afterSeq`、`upToSeq` | 只接受 DO 当前范围内的值 |
| 时间 | 一律使用服务器时间，不采用客户端传来的时间 |

没有会话、票据这一类“验证一次、之后免验证”的机制：**每个请求都自带证明，每次都重新验证。**

### 4.2 鹰角 token 一定会经过 Worker

- 所有权必须由 Worker 自己核实。所以下面这些场景，浏览器**一定要把鹰角 token 交给 Worker**：
  - 密码模式的开通、覆盖（第 7.10 节）、无密码时删除；
  - 无密码模式的每一个请求。
- 传的是 OAuth token：由账号 token 经 grant 换来，是只给“鹰角用户中心”这一个应用的授权，用途比账号 token 窄。
- 但无论传账号 token 还是 OAuth token，Worker 都能看到一个有效的鹰角凭证。所以这部分代码必须放在仓库里显眼的位置，接受公开审计（4.3）。

### 4.3 审计：放在显眼的位置

- **云同步中读取鹰角 token 的代码只有一个文件**：`worker/hg-verify.ts`（放在 worker 目录顶层，文件名直接说明用途）。
  - 只导出一个函数：输入请求头部，输出“核实过的 game + uid”或拒绝。从请求里取 token 也在这个文件里完成。
  - 只请求一个写死的地址（`binding_list`），客户端不能指定。
  - 请求失败、超时、`code` 不为 0、`appCode` 不匹配、响应格式不对，一律按验证失败处理（fail closed）。
  - token 不写入存储，不写日志，不放进返回值，也不放进错误信息。
- **仓库根目录新增 `SECURITY.md`**（GitHub 会在仓库首页和 Security 页显示）。它列出 Worker 里所有会接触鹰角 token 的地方，并链接到代码：
  1. 透明转发（`worker/proxy.ts`、`worker/upstreams.ts`）：拉取记录时，账号 token 经过这里原样转发，不解析；
  2. 所有权核实（`worker/hg-verify.ts`）：云同步时，OAuth token 经过这里，用来查询绑定列表，然后丢弃。
- README 的安全说明和网站的“关于”页都链接到 `SECURITY.md`。
- **CI 加一条检查**：worker 目录下除了 `hg-verify.ts`，任何文件都不允许出现 token 字段名（`oauthToken` 等）。这样以后改代码时，不会在别处悄悄用到 token。
- **线上代码可以对照**：
  - 生产环境只通过公开仓库的 GitHub Actions 部署，运行日志公开；
  - `/api/cloud/v1/info` 返回线上部署的 commit hash，任何人都可以和仓库对照。
- 局限：审计能证明仓库里的代码做了什么，但不能从密码学上保证线上运行的就是这份代码，因为持有 Cloudflare 账号的人可以绕过 Actions 部署。

## 5. 总体结构：信封加密

- 每个云端账号有一把随机的**数据密钥 DEK**（AES-256-GCM），在浏览器里生成。
- 所有记录都在浏览器里用 DEK 加密后再上传。
- 两种模式只差在“DEK 用什么包起来保管”：

| | DEK 用什么包裹 | 在哪里解开 |
|---|---|---|
| 密码模式 | 由密码派生的 `kek` | 只在浏览器 |
| 无密码模式 | 服务器派生的 `KEK_hg`（第 8.3 节） | 浏览器；但服务器随时能算出 `KEK_hg` |

- 知道旧密码时改密码，只需要重新包裹 DEK，不用重新上传数据。
- 覆盖云端（开通、忘记密码、切换模式）一律换一把新 DEK，并上传完整快照。

## 6. 账号标识

```
locator = base64url(SHA-256("arkrecord/cloud-sync/v1/locator" ‖ 0x00 ‖ game ‖ 0x00 ‖ uid))
```

- 每个 locator 对应一个 Durable Object（`idFromName(locator)`），里面存这个账号的全部云端数据。
- locator 只是假名，服务器能穷举反推出 UID（前提 1）。它的作用是：
  - 存储里不直接出现 UID；
  - 不同游戏、不同协议版本互不混淆。
- 密码模式的日常读写只带 locator，不带 UID。

## 7. 密码模式（推荐）

### 7.1 密钥派生

```
salt      = SHA-256("arkrecord/cloud-sync/v1/salt" ‖ 0x00 ‖ game ‖ 0x00 ‖ uid)   // 在本地算出，不经过服务器
oprfOut   = OPRF(k_loc, salt ‖ password)       // 7.2：服务器参与计算，但看不到密码，也看不到结果
stretched = Argon2id(oprfOut, salt, m=32 MiB, t=3, p=1, 输出 256 位)   // 7.7：参数实测后写死
master    = HKDF-Extract(salt, oprfOut ‖ stretched)
authKey   = HKDF-Expand(master, "arkrecord/cloud-sync/v1/auth", 256 位)  // 发给服务器，证明所有权
kek       = HKDF-Expand(master, "arkrecord/cloud-sync/v1/kek", 256 位)   // 只留在浏览器，用来包裹 DEK
```

这个顺序和 OPAQUE（RFC 9807）的密码处理一致：先过 OPRF，再做慢速派生。

**盐由 game + uid 按固定算法算出**：

- 任何设备只要知道 UID，就能算出同一个盐，用户不需要自己同步盐；
- 也不向服务器索取盐。向服务器要盐，本身就会暴露“这个 UID 有没有开通云同步”；
- 盐的作用是让每个账号的散列都不同，没法用一张预先算好的表同时破解所有账号。它不需要保密。

其他：

- Argon2id 的参数写死在协议版本 v1 里，同样不存服务器。以后要升级，就出新版本（见 7.7）。
- `authKey` 和 `kek` 由 HKDF 分开派生：服务器拿到 `authKey`，也推不出 `kek`。
- 所有密钥（`master`、`authKey`、`kek`、DEK）都是 256 位，已经是 AES 的上限。被暴力破解的从来不是密钥，而是**密码**，规则见 7.6。

### 7.2 OPRF 加固：服务器参与派生，但看不到密码

**为什么需要。**如果只在浏览器里做慢速派生，`authKey`、`verifier`、`wrapped_dek` 都只是“密码的确定函数”。其中任何一个泄露，拿到的人都能用显卡离线猜。例如：

- 设备上保存的 `authKey` 被拷走；
- 存储被导出，同时 `SYNC_PEPPER` 也泄露。

目标是：**任何一样东西单独泄露，都不能拿来离线猜密码。**

**做法。**在派生过程中插入一步只有服务器能算的函数：不经意伪随机函数（OPRF，RFC 9497）。

1. **盲化**：浏览器把 `salt ‖ password` 映射成椭圆曲线上的一个点，乘以一个随机数 r，发给 Worker。Worker 看到的只是一个随机点，得不到任何关于密码的信息。
2. **计算**：Worker 用这个账号专属的密钥 `k_loc = HKDF(SYNC_OPRF_KEY, locator)` 乘上去，返回结果。
3. **去盲**：浏览器把结果除以 r，得到 `oprfOut`。Worker 不知道最终结果是什么。

**效果。**

- 没有 `SYNC_OPRF_KEY`，就算不出任何一个猜测对应的 `oprfOut`，也就没法验证猜测。每验证一次猜测，都必须请服务器算一次。
- 服务器按账号限制计算次数，于是**所有猜测都变成在线猜**：
  - 每个账号 24 小时内最多 10 次 OPRF 计算。正常用户只在输入密码时算一次。
  - 次数每次都写入存储；成功登录也不重置，防止偷到 `authKey` 的人借成功登录刷新额度。
- **必须按账号派生密钥（`k_loc`）**：如果全站共用一个密钥，攻击者可以借别的账号的额度替目标账号计算，按账号限次就失效了。
- 对不存在的 locator 也照常计算并返回，不暴露账号是否存在。
- 盐仍然在本地算。OPRF 这一步不泄露密码，也不泄露结果。

**泄露情况对照：**

| 泄露了什么 | 能不能离线猜密码 |
|---|---|
| 存储（DO 数据被导出） | 不能：`verifier` 和 `wrapped_dek` 的外层要 `SYNC_PEPPER`，内层要 OPRF |
| 设备上保存的 `authKey` | 不能：每个猜测都要服务器算一次 OPRF，按账号限次 |
| 网络上截获的请求 | 不能：盲化后的点不含任何信息；截获的 `authKey` 同上 |
| 只泄露 Worker secret | 不能：手里没有可以比对的东西 |
| Worker secret + 存储（或 + 某台设备的 `authKey`） | **能**。这时才轮到慢速派生（7.7）和密码强度（7.6）兜底 |

最后一种只会发生在本站运营者、Cloudflare，或者两样都被攻破的时候。

**代价：**

- 输入密码时多一个请求。之后设备上保存的 `authKey` 直接用，不用再算。
- Worker 每次做一次椭圆曲线标量乘法，毫秒级，需要实测确认在免费版每个请求 10 ms 的 CPU 上限之内。
- 用现成的、经过审计的实现，例如 `@noble/curves` 的 RFC 9497 OPRF，或者 Cloudflare 的 `voprf-ts`（实现前再确认），并在 CI 里用 RFC 9497 的测试向量验证。
- **`SYNC_OPRF_KEY` 和 `SYNC_PEPPER` 必须离线备份**。丢了，所有密码模式的云端数据都再也解不开。本地数据不受影响，用户可以用“覆盖”重建。

### 7.3 服务器保存什么

| 字段 | 内容 |
|---|---|
| `verifier` | `HMAC-SHA256(SYNC_PEPPER, authKey)`，其中 `SYNC_PEPPER` 是 Worker secret |
| `wrapped_dek` | 用 `kek` 包裹的 DEK，外面再用 `HKDF(SYNC_PEPPER, locator)` 加密一层 |
| 批次 | 密文（第 9 节） |

服务器不保存：密码、`authKey`、`kek`、DEK 明文。

外面那层服务器加密，是为了防“只拿到存储”的情况（例如数据被导出）。没有 `SYNC_PEPPER` 的话，`verifier` 不能用来验证密码猜测，`wrapped_dek` 也解不开，所以连离线猜密码都做不到。

### 7.4 证明所有权

- 每个请求都带 `{ locator, authKey }`。DO 计算 `HMAC(SYNC_PEPPER, authKey)`，和 `verifier` 做常量时间比较，通过才返回 `wrapped_dek` 和密文，或者才接受写入。
- **只知道 UID**：能算出 locator，但没有 `authKey`，什么都拿不到，连密文也没有。
- **locator 不存在**和**密码错误**返回完全相同的 401，耗时也尽量一致，不能用来判断某个 UID 有没有开通。
  - 对不存在的 locator，在 DO 内存里模拟同样的退避（不写存储）。DO 被回收后计数会清零，所以只能尽量遮掩。
  - 最坏情况下，有心人能看出某个 UID 有没有开通云同步，但拿不到任何数据。
- `authKey` 只放在请求体里，不放 URL，也不放请求头。Worker 不记录日志（observability 已关闭）。
- `authKey` 只能用来证明身份、取回密文，不能解密。

### 7.5 防猜密码

核心：**没证明之前什么都不给。**

- 核对通过之前，服务器不返回密文，也不返回任何能用来验证猜测的东西（`verifier`、`wrapped_dek` 都不出 DO）。
- 派生过程中有一步只有服务器能算（OPRF，7.2）。所以即使有东西泄露，每验证一次猜测也都必须请服务器算一次。
- 所以外人没办法离线猜，每猜一次都必须经过 Worker。显卡再快也用不上：猜密码的速度上限就是 Worker 允许的速度。

**第一道闸：Worker 限速（决定性的一道）**

- **按被猜的账号（locator）退避**：
  - 连续失败 5 次后开始指数退避：1、2、4……分钟，最长 1 小时；成功一次就清零。
  - 按账号计，不按攻击者的 IP 计。攻击者换再多 IP、动用再多机器，同一个账号第一天也只能试三十次左右，之后每小时一次。速度上限是固定的，不取决于他能把 Cloudflare 打多快而不被拦下。
  - 退避期间一律返回“请稍后再试”，**不核对密码**，攻击者不能借退避期间继续试。
  - 失败次数**每次都写入存储**，不只放在内存里。否则攻击者可以等 DO 被回收、计数清零后再试。每天的写入额度和请求额度一样是 10 万，所以这不会额外放大被刷额度的风险。
- **按账号限制 OPRF 次数**：24 小时内最多 10 次（7.2），偷到 `authKey` 的人也只能按这个速度猜。
- **按 IP 限速**（`RL_CLOUD`）：挡住单一来源的刷量，保护免费额度。
- 副作用：知道你 UID 的人可以故意输错，让你这个账号暂时只能慢速认证。不会永久锁定，本地数据也不受影响。

**第二道闸：慢速派生**

- 每猜一次，都要先算一次 Argon2id（7.1、7.7）。正常设备只在输入密码时算一次，结果缓存起来，不影响使用。
- Argon2id 是**内存困难**的：每猜一次都要占用几十 MB 内存，显卡的并行度被内存带宽卡住，比 PBKDF2 这类纯计算的派生更难用显卡加速。
- 对外人这一点无关紧要，因为他们只能在线猜。它只影响下面“离线猜”的情况。

**离线猜**：

- 只拿到存储、只拿到某台设备的 `authKey`、只拿到 Worker secret，都做不到（7.2 的对照表）。
- 只有同时拥有 Worker secret 和（存储或某台设备的 `authKey`）的人才能离线猜，也就是本站运营者、Cloudflare，或者两样都被攻破。速度取决于显卡。
- 粗略估计（数量级，参数实测后再更新）：用 PBKDF2（60 万次）时，一块高端显卡每秒能试一两万个密码；用 Argon2id（32 MiB、3 遍）时，大约少一到两个数量级。

| 密码 | 约多少位 | 一块显卡猜中大约要 |
|---|---|---|
| 常见密码、简单规律（`Abcd12345678`） | 字典里就有 | 秒级；7.6 的屏蔽规则会直接拒绝 |
| 人想出来、看着随机的 12 位 | 30～40 位 | PBKDF2 时几小时到一两年；Argon2id 时再长一到两个数量级 |
| 真正随机的 12 位（大小写 + 数字） | 约 71 位 | 不可能 |
| “生成”按钮给的 16 位 | 约 93 位 | 不可能 |

### 7.6 密码规则

**强制**（全部在浏览器里检查，服务器看不到密码）：

- 至少 12 位；
- 必须同时有大写字母、小写字母和数字；
- **屏蔽常见的简单密码**：
  - 泄露密码库里的常见密码。只收录满足长度和字符种类要求的条目，更短的本来就会被前两条规则拒绝，所以内置的表很小。
  - 简单规律：连续（`abcd`、`1234`、`4321`）、重复（`aaaa`、`1111`、`abcabc`）、键盘顺序（`qwerty`、`asdf`、`1qaz2wsx`）。
  - 常见单词加数字或年份：`Password2024`、`Abcd12345678`；以及和游戏、本站有关的词：`arknights`、`endfield`、`kaltsit`、`doctor`、`amiya`、`rhodes`。
  - 检查时不区分大小写，并还原常见的字符替换（`@→a`、`0→o`、`1→l/i`、`3→e`、`$→s`）。
- 不能包含 UID 或昵称。

这些检查只在浏览器里做。改过的网页可以绕过，但只会削弱用户自己的账号。

**建议**（界面上写明）：

- 16 位以上，或者点“生成”。
- “生成”给出 16 位随机密码：大小写 + 数字，去掉容易看混的 `0 O 1 l I`，约 93 位。生成后提示用户自己保存。

**为什么 12 位 + 字符种类 + 屏蔽规则够用**：

- 对外人，只能在线猜，被按账号的退避卡住（7.5）；只拿到存储也没用。
- 只有同时拥有存储和 secret 的人能离线猜，这时真正决定安全的是密码有多随机。想防住这种情况，按建议用生成的密码。

### 7.7 慢速派生：Argon2id，保证一定算得出来

原则：**慢可以接受，算不出来不行。**派生结果是固定的值，每台设备只在输入密码时算一次，之后缓存起来（7.8）。所以只要不是慢到极端，就不是问题。

“算不出来”可能来自三个方面，分别这样处理：

1. **浏览器不能运行 WebAssembly。**
   - 例如 iOS 锁定模式（Lockdown Mode）会禁用 WebAssembly 和 JIT；一些企业管理的浏览器也会禁用；不认识 CSP `'wasm-unsafe-eval'` 的旧浏览器（Safari 16 以前等）也编译不了。
   - 处理：实现随网站一起发布，**两套**：WebAssembly 版（快，例如 hash-wasm）和纯 JS 版（例如 `@noble/hashes`）。先试 WebAssembly，不行就自动换纯 JS。只要浏览器能运行这个网站，就能算出来，只是快慢不同。
2. **两套实现结果不一致**（会导致某台设备算出来的钥匙对不上）。
   - CI 里用 RFC 9106 的测试向量验证两套实现，再用随机输入交叉比对，必须逐字节相同。
   - 浏览器第一次使用前，先用一组固定测试向量自检；自检不通过就换另一套实现。两套都不通过，就明确报错，不会算出一个错的结果去覆盖云端。
3. **内存分配失败。**
   - 这是真正可能“彻底算不出来”的地方，所以不追求大内存：用 **32 MiB、3 遍**（以时间换内存）。几十 MB 对能运行这个网站的设备都不是问题（网站本身的图表就要占用这个量级）。
   - 参数按“最慢的环境也能算完”来定：实测 iOS 锁定模式（纯 JS、无 JIT）和低端安卓手机。如果耗时超过一两分钟，就降低内存、增加遍数，然后写死在协议版本里。

其他保证：

- **不卡界面**：在 Web Worker 里计算，按遍数显示进度。
- **旧版本永远算得出来**：以后升级参数或算法，旧协议版本的实现永远保留，已经开通的账号永远能派生出原来的钥匙。
  - 升级方式：在一台设备上输入密码时，用新参数重新派生、重新包裹 DEK（流程同 7.9 改密码），其他设备下次输入密码时跟着升级。不会自动降级。
- **万一某台设备确实算不出来**：只是那台设备用不了云同步，本地数据和其他设备都不受影响。
- **CSP**：`script-src` 加 `'wasm-unsafe-eval'`，只允许编译 WebAssembly，不允许 JS 的 `eval`。不认识这个关键字的旧浏览器会自动走纯 JS 实现。
- **输出**：Argon2id 输出 256 位。它没有 PBKDF2 那种“输出超过哈希长度就分段、多算的部分只拖慢自己”的问题，但 256 位已经够用。

### 7.8 在浏览器里保存

- 不保存密码原文，也不保存 Argon2id 的中间结果；只保存用得到的最终值：
  - `authKey` 保存原始字节，因为每次请求都要发给服务器；
  - DEK 解开时设为**不可导出**的 `CryptoKey`，存进 IndexedDB。页面脚本可以用它加解密，但读不出它的原始字节。
- 这些值相当于这个账号云端数据的钥匙：只存在本机，不导出，不进快照，不同步。“退出云同步”时删除。
- 可以选“不在这台设备保存”，每次云同步时再输入密码。
- 清除浏览器数据之后，需要重新输入密码。

### 7.9 改密码（知道旧密码）

- 新密码先按 7.1 派生（其中一次 OPRF，计入当天次数）。请求带旧 `authKey`，上传新的 `authKey` 和新的 `wrapped_dek`。DO 在一个事务里原子替换。
- 不用重新上传数据。
- 其他设备下一次请求会收到 401，提示“密码已在别处修改，请重新输入”。

### 7.10 忘记密码：用最全的浏览器覆盖云端

密码丢了，云端的数据就再也解不开了，所以没有“找回”，只有“覆盖”：

1. 用户选一个自己认为数据最全的浏览器，在那里操作。
2. 浏览器提供：UID、证明拥有这个 UID 的有效鹰角 token、新密码。
3. 浏览器按 7.1 派生新密码的 `authKey` 和 `kek`（其中一次 OPRF），生成新 DEK 并用 `kek` 包裹；把本地这个账号的全部记录打成快照，用新 DEK 加密。
4. Worker 向鹰角核实 token（第 8.2 节），用核实过的 uid 自己计算 locator。
5. DO 在一个事务里删除旧的全部批次，换上新的 `verifier` 和 `wrapped_dek`，写入快照。旧密文反正已经解不开，直接删除。

覆盖之后：

- 其他设备下一次请求会收到 401，提示“云端已被覆盖或密码已修改，请输入新密码”。
- 输入新密码后，那台设备会把云端没有的记录补传上去（并集）。所以只存在于其他浏览器里的记录也不会丢，只要那个浏览器还在。
- 鹰角 token 在密码模式里**只能覆盖或删除，不能读取**。偷到你鹰角 token 的人最多覆盖掉云端副本，读不到原来的内容。
  - 你用自己的 token 再覆盖回来即可。
  - 你的设备不会把数据传给对方，因为它不知道对方设的密码。

**开通**和覆盖是同一个操作：云端还没有这个 locator 时，覆盖就是开通。开通也必须验证鹰角 token：locator 可以由 UID 算出来，如果谁都能开通，知道你 UID 的人就可以抢先用他自己的密码占住你的位置。

## 8. 无密码模式（鹰角 token 验证，不推荐）

### 8.1 保护范围（放在开启界面和文档最显眼的位置）

| 情况 | 结果 |
|---|---|
| 只知道 UID / hgId | ✓ 拿不到任何东西 |
| 只拿到存储（数据被导出），没有 Worker secret | ✓ 解不开 |
| 本站运营者（持有 Cloudflare 账号和 Worker secret） | ✗ 技术上可以解密，只能依靠公开代码和运营者不作恶 |
| Cloudflare | ✗ 技术上可以解密 |
| 任何人拿到你**有效**的鹰角 token（失效之前） | ✗ 能读取你的云端记录 |

- 原因见前提 2：不存在一种密钥，既能由鹰角账号派生，又是服务器算不出来的。
- 开启时要求用户逐条勾选确认上面三条 ✗。界面上默认推荐密码模式，无密码模式放在“其他方式”里。

### 8.2 每个请求都由 Worker 向鹰角核实

1. 浏览器：账号 token → grant 得到 OAuth token。这一步现在就有，经 `/api` 转发。
2. 浏览器在**每个**云同步请求里带上 `{ game, uid, oauthToken }`。
3. Worker 用 `oauthToken` 调 `binding_list?appCode={game}`（服务器到服务器，地址写死）。
4. 必须同时满足以下条件，任何一条不满足，或者请求失败、超时，都返回 403：
   - HTTP 200，`code` 为 0；
   - 列表里对应项的 `appCode` 等于 `game`；
   - 绑定列表里有这个 uid（字符串完全相等）。
5. Worker 根据核实过的 uid 自己计算 locator，然后才访问 DO。核实失败的请求不会产生 DO 请求。
6. `oauthToken` 用完即丢：不保存，不记录。

其他说明：

- 鹰角接口出问题时，无密码模式就用不了（fail closed）。
- OAuth token 失效后就不能再用来证明所有权，它的有效期需要实测（第 16 节）。

### 8.3 密钥

```
KEK_hg = HMAC-SHA256(SYNC_HG_SECRET, "arkrecord/cloud-sync/v1/hg" ‖ 0x00 ‖ locator)
```

- 核实通过后，Worker 在响应里带上 `KEK_hg`，浏览器用它解开 `wrapped_dek`。
- 加解密仍然在浏览器里进行，服务器平时只存密文。但服务器随时能算出 `KEK_hg`，所以它能解密。
- 为什么一定要掺入 `SYNC_HG_SECRET`：
  - 如果只用 uid 派生，任何知道 uid 的人都能算出密钥，保护就只剩下“不给你密文”这一道门。
  - 掺入之后，至少“只拿到存储”的情况是安全的。
- 密文头里带 `kid`，以后可以轮换 `SYNC_HG_SECRET`。
- `worker/hg-verify.ts` 和 `SECURITY.md` 的开头写明 8.1 的保护范围。

### 8.4 切换模式

- 两个方向都用“覆盖”（7.10）：换新 DEK，上传完整快照。
- 从无密码模式切到密码模式时，必须换新 DEK，因为旧 DEK 服务器能算出来。
- 从密码模式切到无密码模式时，要明确警告。

## 9. 数据格式与密度

### 9.1 实测：列式编码比直接压缩 JSON 小 10 倍

用演示数据生成器拼出一个“老玩家”（35,240 抽）实测：

| 编码 | 大小 | 每抽 |
|---|---|---|
| JSON 原样（本地存储的字段） | 9.98 MB | 283 B |
| JSON + deflate | 703 KB | 20 B |
| 列式 JSON | 493 KB | 14 B |
| **列式 + deflate** | **72 KB** | **约 2 B** |

演示数据是模拟的，真实数据会有出入，但数量级相同。按每抽约 2 字节，1 MiB 可以装下约 50 万抽，任何账号的完整快照都能放进一个请求、存成一行。

### 9.2 列式编码（明文）

- 按全序排序后按列存储，而不是一条一条存对象。
- 重复的内容放进字典，列里只存序号。字典项是完整的元组，不预设“同一个 id 一定对应同一个名字”：
  - 明日方舟：卡池 `[poolId, poolName, category]`、干员 `[charId, charName, rarity]`；
  - 终末地：卡池 `[poolId, poolName, poolType, type]`、物品 `[itemId, itemName, rarity]`、`kind`。
- 时间存相邻两条的差值。同一次十连的差值是 0，压缩后几乎不占空间。
- 布尔值（`isNew`、`isFree`）存成位串，`source` 存成枚举。
- 可推算的字段只在与推算结果完全相同时才省略（见 9.3 的“全覆盖性”）。
- 源石/充值：`kind`、`key`、`ts` 按列存，`raw` 按 RFC 8785 规范化。终末地卡池信息只存记录里用到的卡池。
- 账号信息（昵称、渠道、观察时间）放在头部。
- 云同步**不复用导出文件格式**：导出格式导入终末地记录时会把 `source` 改成 `import`，不是无损的。云同步直接对本地表的字段编码。

### 9.3 编码规范：四个性质

先定义编码的对象，再逐条说明四个性质：定义、怎么保证、怎么测。

**数据模型**

- 一个账号的云端内容 = 几个记录集合（明日方舟寻访、终末地寻访、源石/充值、终末地卡池信息）+ 账号信息。
- 每条记录只包含所属类型声明的字段。字段值只能是：字符串、安全整数、布尔、`null`、缺省。
  - 字符串原样保存，不做 Unicode 规范化。含有不成对代理项（无法用 UTF-8 表示）的字符串直接报错。
  - `undefined` 等同于缺省。这是唯一的一条归一化规则，写进规范。
  - 源石/充值的 `raw`、卡池的 `items` 是任意 JSON 值，按 I-JSON 处理。
- 每条记录有唯一的键：寻访是 `key`，源石/充值是 `kind + key`，卡池是 `poolId`。同一个集合里，一个键只能出现一次。

**1. 全覆盖性（无损）**

- 定义：对任何合法的 S，`decode(encode(S))` 和 S 逐字段完全相同，包括“缺省 / `null` / 空字符串”三者的区别。
- 保证：
  - **字段表穷举**：每种记录类型用一张字段表写明每个字段怎么编码，写成 `satisfies Record<keyof AkPull, …>`。以后 `AkPull` 加了字段而字段表没跟上，TypeScript 编译直接报错。
  - **不静默丢弃**：编码时遇到字段表以外的字段、或者类型不对的值，直接报错。
  - **推算字段走例外列**：`tsSec`、标准格式的 `key` 只在与推算结果（`floor(gachaTs / 1000)`、`poolId:charId:gachaTs:pos` 等）完全相同时才省略；不同时存进例外列。即使出现异常数据也不会丢。
  - `accountId` 不存，由所在账号决定。
  - **版本门槛**：浏览器遇到自己不认识的更高格式版本时，只读不写，并提示刷新网页。否则旧代码解码新格式时会丢掉新字段，再合并上传，就把新字段永久抹掉了。

**2. 无歧义性**

- 定义：任何一段字节，要么被拒绝，要么只能解码成唯一的一个 S。
- 保证：
  - **结构化编码，不用分隔符拼接字符串。**9.1 实测时用 `\0` 拼接只是为了估算大小，规范里不用。
  - **“缺省”和 `null` 用单独的存在位图表示**，不用哨兵值。
  - **可能是数字、也可能是字符串的列**（终末地 `seqId`）：只有规范的十进制整数（无前导零、在安全整数范围内）才转成数字差分存储，其他原样存字符串，用标记位区分。
  - **解码严格校验**，任何一条不满足就整批拒绝：
    - 各列长度一致，字典序号在范围内，位图长度精确；
    - 长度前缀与实际一致，填充字节全为 0，没有多余数据；
    - 版本号和类型都认识。

**3. 规范唯一性**

- 定义：同一个 S 只有一种编码，解码器也只接受这一种。
- 保证：
  - **记录按全序排列**，排序键的最后一项都是唯一键，所以不会出现并列：
    - 明日方舟寻访：`(gachaTs, pos, key)`；
    - 终末地寻访：`(gachaTs, key)`；
    - 源石/充值：`(kind, ts, key)`；
    - 卡池：`poolId`。
  - **字典项**按在排序后的记录里第一次出现的顺序排列，不允许重复项，也不允许没被用到的项。
  - **整数**用最短形式（无前导零、无 `-0`、无指数），只允许安全整数。时间差相对于上一条计算，第一条相对于 0。
  - **对象**字段顺序固定、无空白，由专用的规范写入器输出，不依赖 `JSON.stringify` 对任意对象的键顺序。任意 JSON 值（`raw`、`items`）用 RFC 8785（JCS）规范化。
  - **解码后重新编码，必须和输入逐字节相同，否则拒绝。**这一条同时挡住重复键、多余空白、不规范的数字、乱序等所有不规范的形式。
- 范围：规范唯一性定义在压缩前的明文上。deflate 的输出和实现有关，IV 是随机的，所以压缩后、加密后的字节不要求唯一。
- 用途：`SHA-256(规范明文)` 可以当作这组数据的**指纹**。
  - 两台设备指纹相同，就说明数据完全一致，可以跳过不必要的上传。
  - 界面上可以据此显示“已与云端一致”。

**4. 幂等性**

- **编码**：`encode(decode(encode(S))) = encode(S)`，由 1 和 3 直接推出。
- **合并**：合并函数必须同时满足幂等 `merge(A, A) = A`、交换 `merge(A, B) = merge(B, A)`、结合 `merge(merge(A, B), C) = merge(A, merge(B, C))`。
  - 这样无论重复下载、重复上传、批次乱序，还是失败后重试，最后每台设备的结果都一样。
  - 具体规则见第 10.1 节。
- **上传**：
  - 重试时带同一个 `batchId`。DO 发现已有这个 `batchId`，就直接返回原来的 seq，不重复写入。
  - 批次最多 32 个，逐行扫描一遍的成本很小，不需要额外建索引。
  - 合并（snapshot）和覆盖也按 `batchId` 去重。

**测试**（属性测试：随机生成数据，CI 每次都跑）

- **无损**：`decode(encode(S))` 严格等于 S，区分缺省和 `null`。
- **规范**：
  - 打乱 S 里记录的顺序，编码结果不变；
  - 对合法编码做各种篡改，全部被拒绝：翻转一位、调换字典顺序、加一个没用到的字典项、数字加前导零、加空白、重复键。
- **覆盖**：
  - 真实样本（`docs/rewrite/fixtures`）；
  - 覆盖边界值的随机记录：`null`、缺省、空字符串、生僻字和 emoji、最大安全整数、旧版键、不符合标准格式的键。
- **合并**：
  - 用随机集合验证幂等、交换、结合；
  - 再模拟多台设备以随机顺序云同步、随机失败重试，最后所有设备的指纹相同。

### 9.4 压缩、填充与加密

```
列式明文 → deflate-raw（浏览器原生 CompressionStream）→ 长度前缀 + Padmé 填充
        → AES-256-GCM(DEK, 随机 96 位 IV, AAD = "arkrecord/cloud-sync/v1" ‖ locator ‖ 信封头)
信封头：版本 1 B + kid 1 B + 类型 1 B（delta / snapshot）+ batchId 16 B + IV 12 B
信封总开销：47 B（含 16 B 认证标签）
```

- **Padmé 填充**：只把长度向上取整到少数几个有效位，额外开销不超过 12%。服务器只能看到大致大小。原来的“填充到 4 KiB 整数倍”对只有几十字节的小批次太浪费，不再使用。
- **AAD 绑定 locator 和信封头（含 batchId）**：服务器不能把别的账号的密文、或者同一账号的另一批密文冒充成这一批；改动任何一位，解密都会失败。
- 服务器能做的坏事只有删除、扣留、回滚批次，结果是云端缺记录。它污染不了本地数据，因为本地只做并集。
  - 无密码模式例外：服务器有密钥，理论上可以伪造批次。
- 解密后再检查明文头里的 `game`、`uid`，不一致就丢弃。

### 9.5 传输：二进制，不用 base64

- 请求体格式：`application/octet-stream`，内容是 `[2 字节头部长度][头部 JSON ≤ 1 KiB][密文]`。
- 头部 JSON 里是 `locator`、`authKey` 或鹰角 token、`afterSeq` 等小字段。
- Worker 只解析头部，密文原样交给 DO，不经过 base64，也不解析大块 JSON：
  - 体积省 33%；
  - Worker 的 CPU 时间也省下来，适合免费版每次请求 10 ms 的 CPU 上限。
- 下载的响应同理：多个信封直接拼接，每个前面带 4 字节长度。

### 9.6 存储（每个 locator 一个 Durable Object，SQLite）

```
meta(mode, verifier, wrapped_dek, kid, created_at, last_access_day, locked_until)   -- 只有一行
batches(seq INTEGER PRIMARY KEY, batch_id, kind, created_at, blob)                  -- 除主键外不建索引
```

- 除主键外不建索引：索引会额外计入写入行数。
- `last_access_day` 每天最多更新一次，用于自动清理；不在每次读取时都写。
- 限额：
  - 单个请求的密文 ≤ 1 MiB（DO SQLite 单行上限 2 MB）；
  - 每个账号总量 ≤ 4 MiB；
  - 批次数超过 32 时，必须先合并才能继续上传。

## 10. 同步算法（客户端）

本地为每个开通了云同步的账号保存：

- `locator`、`mode`；
- `lastSeq`：已经下载到的最大批次号；
- `remoteKeys`：云端已有的记录键（只存键，不存内容）。

一次云同步最多两个请求：

1. **下载（pull）。**
   - 请求带上证明（密码模式：`authKey`；无密码模式：鹰角 token）和 `lastSeq`。
   - 响应里有 `wrapped_dek`（无密码模式还有 `KEK_hg`）和 `seq > lastSeq` 的全部批次。
   - 浏览器解出 DEK，逐批解密、校验，用现有的幂等合并写入本地，再把这些记录的键加入 `remoteKeys`。
2. **上传（push）。**只在有新记录时才发：
   - 待上传 = 本地键 − `remoteKeys`，打成一个 delta 批次，再带上一次证明上传。
   - 批次数超过 16 时，这一次改为上传 snapshot（本地全部记录，此时已包含云端的全部内容），并注明“覆盖到 seq N”。
   - DO 在一个事务里写入 snapshot，删除 seq ≤ N 的旧批次。其他设备在此期间上传的 seq > N 的批次不受影响。

各种情况：

- **两台设备同时云同步**：各自上传自己的 delta，互不冲突，下一次云同步时互相拉到。不需要锁。
- **新设备**：`lastSeq = 0`，先下载全部，再上传本地多出来的部分。
- **删除**：
  - 并集只增不减，本地删除账号不会删除云端；
  - “删除云端数据”是单独的操作，需要 `authKey`，忘记密码时用鹰角 token。

### 10.1 合并规则（与顺序无关）

同一个键可能出现内容不同的两个版本。例如同一抽在一台设备上来自接口、在另一台上来自导入文件；同一条源石记录，一个是旧版格式，一个是新接口格式。规则必须与合并顺序无关，所以每种记录都在一个**全序**上取最大值：

| 记录 | 保留哪个版本 |
|---|---|
| 寻访 | 来源优先级 接口 > 导入 > 旧版 → 字段更全的 → 规范编码字节序更小的 |
| 源石 / 充值 | 新接口格式 > 旧版格式 → 规范编码字节序更小的 |
| 账号信息（昵称、渠道） | 观察时间更新的 → 规范编码字节序更小的 |
| 终末地卡池信息 | `fetchedAt` 更新的 → 规范编码字节序更小的 |

在全序上取最大值，天然满足幂等、交换、结合。

旧版寻访的覆盖（现有的 ±3 秒匹配逻辑）：

- 被接口数据覆盖的旧版记录，从本地删除，这是合并里唯一的删除。
- 一条旧版记录是否被覆盖，只取决于有没有对应的接口记录，而接口记录只增不减，所以结果和合并顺序无关。
- 实现时用属性测试确认这一点，尤其是“一次十连只同步到一部分”这类边界情况。

**现有代码里要先统一的地方**（第一阶段一起改）：

1. 从鹰角同步时，同键是后写的覆盖先写的；导入文件时，同键是跳过、先写的保留。两种都和顺序有关，要统一成上面的规则。
2. 导出文件导入终末地记录时，`source` 一律变成 `import`，原来的来源就丢了。云同步不复用导出格式（9.2）；导出格式本身也顺手改成保留来源。
3. 源石/充值同键时后写的赢，旧版格式和新接口格式可能互相覆盖。同样改成上面的规则。

## 11. 接口草案

全部是 POST，请求体为第 9.5 节的二进制格式，沿用现有 `/api` 的同源检查、限速和 body 上限。**每个请求都自带证明，没有会话或票据。**

| 接口 | 证明 | 用途 |
|---|---|---|
| `/api/cloud/v1/oprf` | —（按账号限次） | OPRF 计算：输入盲化后的点，返回乘上 `k_loc` 的结果（7.2） |
| `/api/cloud/v1/claim` | 鹰角 token | 开通 / 覆盖：设定模式和新密码，上传完整快照（7.10、8.4） |
| `/api/cloud/v1/pull` | `authKey` 或鹰角 token | 下载 `afterSeq` 之后的批次 |
| `/api/cloud/v1/push` | `authKey` 或鹰角 token | 上传 delta；或者上传 snapshot，并注明覆盖到哪个 seq |
| `/api/cloud/v1/rekey` | 旧 `authKey` | 知道旧密码时改密码（只换包裹） |
| `/api/cloud/v1/delete` | `authKey` 或鹰角 token | 删除这个账号的全部云端数据 |
| `/api/cloud/v1/info` | — | 协议版本、线上部署的 commit hash |

## 12. Cloudflare 免费版额度

依据 Cloudflare 文档（2026-10 查阅）。超出免费额度后，当天这类操作会直接失败，UTC 0 点（北京时间 8 点）重置。

| 限制（免费版） | 额度 | 云同步的用量 |
|---|---|---|
| Workers 请求 | 100,000 / 天（静态资源不算） | 每次云同步 1～2 个 |
| Workers CPU 时间 | 每个请求 10 ms | Worker 只解析 ≤ 1 KiB 的头部、做一次 HMAC；加解密、压缩、慢速派生全在浏览器；OPRF 一次标量乘法（毫秒级，需实测） |
| 子请求 | 每个请求 50 个 | 无密码模式每个请求 1 个（`binding_list`） |
| DO 请求 | 100,000 / 天 | 每次云同步 1～2 个；鹰角核实失败的请求不产生 |
| DO 运行时长 | 13,000 GB-s / 天 | 只在处理请求时计费，每个请求几毫秒到几十毫秒 |
| DO 写入行数 | 100,000 / 天（删除也算） | 每次上传 1 行；合并 1 行 + 删除的旧批次数；每次认证失败、每次 OPRF 计算各 1 行 |
| DO 读取行数 | 5,000,000 / 天 | 每次下载 = 新批次数 + 1 |
| DO 存储 | 账号总共 5 GB | 每个账号通常几十 KB；按每个 100 KB 算可以容纳约 5 万个 |
| 请求体 | 100 MB | 单个请求 ≤ 1 MiB |

- 旧版统计显示近 30 天的活跃用户在一两百人的量级，离这些额度很远。
- 浏览器遇到额度用完的错误时提示“云端今天的额度已用完，北京时间 8 点后再试”，本地不受影响。

## 13. 威胁模型汇总

| 攻击者 | 密码模式 | 无密码模式 |
|---|---|---|
| 只知道 UID | 拿不到任何东西 | 拿不到任何东西 |
| 知道 UID，猜密码 | 只能在线猜：按账号退避，第一天约 30 次，之后每小时 1 次，与 IP 数量无关 | — |
| 偷到有效的鹰角 token | 读不到；能覆盖或删除云端副本（本地不受影响，用自己的 token 覆盖回来） | **能读取** |
| 偷到这台设备上保存的 `authKey` | 只能下载密文，解不开；想猜密码也必须请服务器算 OPRF，按账号限次 | — |
| 只拿到存储（数据被导出） | 无用（缺 `SYNC_PEPPER` 和 `SYNC_OPRF_KEY`） | 无用（缺 `SYNC_HG_SECRET`） |
| 运营者 / Cloudflare（存储和 secret 都有） | 看不到明文；可以离线猜弱密码（7.5、7.7） | **能解密** |
| 网络中间人 | TLS | TLS |
| 大量请求刷光免费额度 | 当天云同步不可用，本地不受影响；按 IP 限速缓解 | 同左 |
| 服务器篡改、调换密文 | AES-GCM + AAD 能检测；只能删除、回滚 | 能伪造 |

**网页应用的共同局限**：两种模式都依赖网站下发的前端代码是诚实的。如果网站被篡改、下发了恶意脚本，脚本可以在你输入密码时把它偷走。这是所有网页端加密的通病。缓解办法：

- 前端开源，只从公开的 CI 构建；
- 严格的 CSP；
- 以后的电脑应用（路线图）可以用签名的安装包提供更强的保证。

## 14. 服务器能看到的元数据

- locator（可以反推出 UID），也就是“哪些 UID 开通了云同步”。
- 模式、批次的数量和大致大小（Padmé 粒度）、上传下载的时间。
- 请求 IP：Worker 不保存，但 Cloudflare 网络层能看到。
- 开通、覆盖，以及无密码模式的每个请求：Worker 会看到 UID 和 OAuth token，用完即丢，不保存。

## 15. 数据保留

- 暂不自动删除不活跃的云端账号。以后需要时再加（DO alarm），加之前会在网页上提前说明。
- 用户可以随时删除。
- 每个账号 4 MiB 的上限保留，作为防滥用措施，防止有人占满免费版的 5 GB 存储。按每抽约 2 字节算，正常账号远远用不到。

## 16. 实现前需要实测

- grant 得到的 OAuth token 多久失效；Worker 直接调用 `binding_list` 是否正常（现有转发就是这样调用的，预计没有问题）。
- 终末地 `binding_list?appCode=endfield` 返回的 uid，是否和本地账号 id 里的一致。
- Argon2id（32 MiB、3 遍）在各环境下的耗时和内存：桌面浏览器、中低端安卓、iOS，以及 iOS 锁定模式（纯 JS、无 JIT）。据此最终确定参数。
- OPRF 在 Worker 里一次计算的 CPU 时间（免费版上限 10 ms），以及选用的实现能否通过 RFC 9497 的测试向量。
- 用真实账号的数据核对 9.1 的密度估计，以及 9.3 的四个性质。

## 17. 决定

已定：

1. **防猜密码的核心**：核对通过之前什么都不给；Worker 按账号退避（与 IP 无关）+ 慢速派生（7.5）。
2. **盐**：由 game + uid 按固定算法算出，不需要用户同步，也不经过服务器。
3. **密码模式的读写只需要 UID + 密码**，不需要鹰角 token。
4. **无密码模式的每个请求都必须带有效的鹰角 token**，由 Worker 当场核实。没有会话或票据。
5. **忘记密码 = 用最全的浏览器覆盖云端**（鹰角 token 证明所有权 + 新密码 + 完整快照）。开通是同一个操作。
6. **密码规则**：强制至少 12 位，同时有大写、小写、数字，并屏蔽常见的简单密码；建议 16 位以上或使用“生成”。
7. **鹰角 token 相关的 Worker 代码集中在 `worker/hg-verify.ts`，由根目录 `SECURITY.md` 指向，CI 检查别处不出现 token 字段。**
8. **数据密度**：列式编码 + deflate-raw + Padmé，二进制传输，目标是不需要升级付费版。
9. **慢速派生用 Argon2id**（7.7）：慢可以接受，必须保证一定算得出来——WebAssembly + 纯 JS 两套实现、测试向量与自检、适中内存，结果在每台设备上缓存。
10. **数据保留**：暂不自动删除；保留每个账号 4 MiB 的防滥用上限。
11. **编码规范**：必须满足幂等性、全覆盖性、无歧义性、规范唯一性（9.3），合并必须与顺序无关（10.1），全部用属性测试保证。

仍待确认：

1. **加入 OPRF 加固**（7.2，推荐）：任何一样东西单独泄露都不能用来离线猜密码；代价是多一个 Worker secret（必须离线备份），输入密码时多一个请求。
2. 无密码模式放到第二阶段，默认藏在“其他方式”里，开启时逐条勾选确认风险。

## 18. 部署需要新增的配置（实现时再加）

- Worker secrets：`SYNC_PEPPER`、`SYNC_OPRF_KEY`、`SYNC_HG_SECRET`。
  - 预览和生产各一套，各自是 32 字节随机数。
  - 直接在 Cloudflare 后台设置为 Secret 类型，不经过 GitHub。`wrangler deploy` 不会覆盖已有的 secret。
  - **生产环境的这几个值必须另外离线备份**（例如密码管理器）。丢了 `SYNC_PEPPER` 或 `SYNC_OPRF_KEY`，所有密码模式的云端数据都再也解不开；丢了 `SYNC_HG_SECRET`，无密码模式的云端数据也一样。
- Durable Object：绑定 `CLOUD` → 类 `CloudVault`，迁移 `v3`（`new_sqlite_classes`，免费版可用）。
- Rate Limiting：`RL_CLOUD`（每 IP 每分钟 20 次）。
- 仓库根目录的 `SECURITY.md`，以及 CI 里的 token 字段检查（第 4.3 节）。
- CSP 的 `script-src` 加 `'wasm-unsafe-eval'`（Argon2id 的 WebAssembly 版，7.7）。
