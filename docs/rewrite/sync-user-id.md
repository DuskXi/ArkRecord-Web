# 同步识别码（设计草案，2026-10-19）

维护者的要求（原话）：“加入同步随机识别码，开通同步的时候识别码就生成，后续存在浏览器里面无论开关都不删除，开了同步就往同步里面传，跨账号共享识别码，作为真独立用户识别，只有冲突的时候询问一下用户。”

维护者另外定的两条：

- 网页版的统计也上报识别码，但仍然要用户在统计同意里选“全部接受”；桌面版默认开启（和桌面版其他统计一样）。
- 冲突时用户选“是同一个人”，保留**先生成的**那个识别码。

还没实现，先给维护者确认。

## 识别码是什么

- 128 位随机数（`crypto.getRandomValues`），写成 32 位十六进制，附带生成时间（毫秒）：`{ id, createdAt }`。
- 不包含、也推不出任何账号、设备或个人信息。
- 一台设备（一个浏览器，或者桌面版）只有一个，同一个人的所有账号共用。

## 存在哪里，什么时候删

- 存在本地 IndexedDB 的 `kv` 表（`sync-user`）。网页版和桌面版都是这样存的；桌面版的识别码和设备统计用的随机设备编号是两回事，互不关联。
- **任何开关都不删它**：关闭云同步、删除云端数据、忘记密码、关闭统计、删除账号，都不删。
- 只有用户清除浏览器数据（或者删掉桌面版的数据目录）时才会没有。之后再同步时，会从云端把它找回来（见下面“生成和沿用”）。

## 随同步数据上传

- 放在每个账号云端数据头部的账号信息里：`account.user = { id, createdAt }`。云同步是端到端加密的，**服务器看不到识别码**。
- 合并规则：两份数据的 `user` 不同时，取 `createdAt` 更早的；时间相同时取 `id` 字典序更小的。规则和顺序无关，满足现有合并的幂等、交换、结合要求（cloud-sync.md 10.1）。
- **格式版本**：带 `user` 的数据写成**版本 3**。按现有的版本门槛规则，没有更新的旧网页读到版本 3，只读不写，并提示刷新网页。
  - 后果：上线以后，开着云同步的账号会陆续写成版本 3。还开着旧网页的设备，刷新一次就恢复正常，数据不会丢。
  - 规范唯一：没有 `user` 时照旧写成版本 1 或 2。

## 生成和沿用

开通或同步某个账号 A 时，设本机识别码为 D（可能没有），A 在云端的识别码为 C（可能没有）：

| D | C | 做什么 |
|---|---|---|
| 没有 | 没有 | 生成新的 D，A 的数据带上 D |
| 有 | 没有 | A 的数据带上 D |
| 没有 | 有 | 本机沿用 C（D = C），不生成新的 |
| 有 | 有，相同 | 什么都不做 |
| 有 | 有，不同 | **冲突，询问用户**（见下） |

## 冲突时询问

弹窗只在冲突时出现，每个账号最多问一次（回答记在本地）：

> 这个账号的云同步数据里记的是另一个用户识别码。可能是你在别的设备上用过，也可能是别人的账号。是同一个人吗？

- **是同一个人**：保留先生成的那个（`createdAt` 更早的）。本机和本机所有开着同步的账号都改用它，下次同步时随数据上传；其他设备同步到后按合并规则自动改用它，不会再问。
- **不是**（比如借用别人的账号、几个人共用一台电脑）：本机识别码不变；这个账号保留它在云端的识别码，本机以后不会把自己的识别码写进这个账号。
- **以后再说**：这次不改任何东西，下次同步时再问。

## 用于统计

- 统计“独立用户数”：上报识别码加前缀后的 SHA-256，服务器再用 `STATS_UID_SALT` 做 HMAC 才保存（和桌面版的 UID 统计相同）。识别码是 128 位随机数，本身就无法反查；加盐是为了和其他计数统一处理。
- 单独一次请求、每天最多一次，和设备、UID 的上报互不关联。
- 网页版：只在“全部接受”之后上报，由网页直接上报（新增同源接口）。桌面版：交给 Python 后端，默认开启，“关于”页可关闭。
- 只有开通过云同步的设备才有识别码，所以这个数是“用过云同步的独立用户数”。
- 网页版“关于”页现在写着“不生成或上传任何可以识别你的标识符”，上线前要改成如实说明；SECURITY.md 同步更新。
