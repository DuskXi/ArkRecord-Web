# 森空岛截图识别

目标：用户上传森空岛的干员列表截图，在浏览器里识别出每个干员（名字、终末地的潜能），
补全图鉴里只靠寻访记录统计不到的部分。全部在前端完成，截图不上传。

状态：**已接入图鉴页**（“导入森空岛截图”）。识别代码在 `src/lib/screenshot/`，保存和合并在 `src/lib/roster.ts`，
界面在 `src/components/roster/RosterImportDialog.vue`。

## 只按名字认干员

干员只按名字认，星级从游戏数据里查，不从截图里读（截图里的星级只在实验阶段用来缩小候选范围）。
候选名单：明日方舟是游戏数据里全部可以拥有的干员（434 个，不含预备干员等），终末地是全部角色（34 个）。

## 认名字的三个信号，以及手动选择

| 信号 | 擅长 | 不擅长 |
|---|---|---|
| OCR + 编辑距离 | 长名字，认错一两个字也能纠正 | 生僻的单字名：“锏”认成“铜”、“黍”认成“了” |
| 截图字形：把候选名字画出来，和截图里的名字比形状 | 单字名、长名字 | 截图很小（名字只有 8 像素高）时把握不大 |
| OCR 认错的字的字形：把 OCR 的结果也画出来，和候选名字比形状 | OCR 认成长得像的字（“铜”→“锏”） | OCR 什么都没认出来 |

- 两个以上信号指向同一个名字时判为有把握；只有一个信号很有把握时也采用；都没把握时给出猜测，标为“请确认”；
- 一张截图里每个名字只分配一次，先分配把握大的；
- **第二道保险是手动选择**：没认出、把握不大的排在核对列表最前面，可以输入名字搜索选择正确的干员，也可以选择“不导入”。
  同一张截图里两张卡片选了同一名干员时必须改正才能保存。

“锏”的例子（缩小到 720 宽，名字约 17×17 像素）：OCR 认成“铜”，编辑距离对不上任何名字；截图字形最像“锏”（0.38，第二名 0.22），
单独不够把握；“铜”画出来和“锏”的相似度 0.64，第二名只有 0.24。两个信号一致，判为“锏”，有把握。

## 截图时间与幂等（`roster.ts`）

保存的是**截图那一刻的状态**：每名干员一条记录，带截图时间 `observedAt`。

- 同一张截图重复导入：时间相同、内容相同，什么都不变；
- 更早的截图不会覆盖更新的；几张截图有重叠时用最新的那张；
- 截图之后又抽到的、又获得赠送的，不改快照，显示时用寻访记录往上加：
  现在的份数 = 截图时的份数（终末地 = 潜能 + 1）+ 截图之后抽到的 + 截图之后的信物赠礼，潜能 = min(份数 − 1, 5)；
- 截图之前的寻访记录比截图上的份数还多时，图鉴里标出来请用户检查（截图时间或潜能可能不对）。

截图时间从文件名读（`Screenshot_2026-10-17-06-05-25-51.jpg`、`IMG_20261017_060525.jpg`、`截屏2026-10-17 06.05.25.png` 等），
读不出时用 JPEG 的 EXIF，再不行用文件的修改时间（可能是传输时间，界面上提示核对），都可以手动修改。

快照会进入导出文件、本地快照和云同步（云同步数据格式版本 2，见 cloud-sync.md 9.2）。多台设备之间按
（截图时间，导入时间，规范编码）取最大的一条，合并结果与顺序无关；同一张截图在一台设备上重复导入不会改变任何东西。

## 累计寻访赠送（`src/lib/stats/gifts.ts`，两个游戏通用）

赠送不是抽出来的，不计入任何寻访统计，单独列出；给了干员 / 武器一份的计入图鉴（终末地潜能 +1）。

终末地：寻访记录接口里 `kind` 以 `gift` 开头的是赠送：`gift_operator_token`（信物赠礼，当期 UP 6★ 的信物）、
`gift_intel_book`（寻访情报书）、`gift_weapon`（武器赠礼，当期 UP 6★ 武器）、`gift_weapon_box`（武库赠礼，自选箱）、`gift`。
接口的赠送条目一般**没有干员 / 武器的 ID 和名字**（官方页面显示的是 `nameText`），所以按卡池补上：
信物赠礼是这个卡池的当期 UP 6★，武器赠礼是当期 UP 武器；`nameText` 里提到了某个干员时优先用它；
辉光庆典这类 UP 不止一个、送的是自选信物的卡池不硬猜。之后同步的新记录会保存 `nameText`。

规则（官方卡池说明）与推算：

| 卡池 | 规则 | 计数 |
|---|---|---|
| 终末地特许寻访 | 每累计寻访 240 次送当期 UP 的信物（`CHAR_UP_6_ITEM_TIME`） | 本期卡池内，不含免费十连 |
| 终末地重构寻访 | 同上 | 同一卡池累计（继承到下一次同名重构寻访） |
| 终末地武库申领 | 累计申领 10 次送武库赠礼，18 次送 UP 武器，之后每 8 次交替（`WEAPON_GIFT_TIME*`） | 每次申领 10 把 |
| 明日方舟限定寻访 | 累计寻访 300 次送限定干员（游戏数据 `limitParam.freeCount`、`limitedCharId`），每个卡池一次 | 本期卡池内 |

记录接口只能查约 90 天（明日方舟的记录里没有赠送条目），本地记录的次数够了而没有对应的赠送条目时按规则推算补上，
标为“推算”；已有的赠送条目先算进去，不会重复。寻访记录页、图鉴、CSV 导出里都和抽到的分开显示。

## 做法

只依赖 RGBA 像素数组（浏览器里来自 canvas 的 `ImageData`），不需要 OpenCV。

| 步骤 | 代码 | 做法 |
|---|---|---|
| 找卡片 | `grid.ts` | 左边缘估计页面背景色 → 按列统计前景比例得到每一列 → 行距用自相关求出 → 长截图是拼接的，行距有几个像素出入，每一行在预计位置附近和“平均卡片”对齐 → 去掉被截断的卡片 |
| 终末地星级 | `endfield.ts` | 卡片最下面颜色条的色相：橙 ≈ 26° 为 6★，金 ≈ 48° 为 5★，紫 ≈ 263° 为 4★ |
| 终末地潜能 | `pentagram.ts`、`endfield.ts` | 见下一节 |
| 明日方舟星级 | `arknights.ts` | 卡片顶部找黄色星星那一行；星星左对齐、间距固定（卡片宽度的 0.0817），以第一颗星为参照逐个星位判断；再用这一排的长度核对 |
| 名字区域 | `text.ts` | Otsu 自动门槛二值化，去掉贯穿整行的线条和装饰（明日方舟名字左边的斜条），裁到文字范围，白底黑字 |
| 名字 | `identify.ts`（`names.ts`、`visual.ts`） | 两个信号：OCR 结果按编辑距离匹配已知名字（长名字很准）；把候选名字用系统字体画出来比字形（生僻的单字名也分得开）。两者一致最可靠；星级只作为偏好；一张截图里每个名字只分配一次，先分配把握大的 |

## 终末地的五角星：潜能

卡片左下角的五角星由 5 笔组成，每一笔是白色、黄色，或者没有画出来。在 30 张卡片上读出来的规律：

| 读到的笔画（按解锁顺序 0→4→3→2→1） | 卡片 | 推断 |
|---|---|---|
| 只有 0 是黄色 | 洁尔佩塔、诀、弭弗、汤汤、梨诺 | 潜能 0 |
| 0 白，4 黄 | 莱万汀、骏卫、别礼、提弗洛斯 | 潜能 1 |
| 0、4 白，3 黄 | 余烬、黎风 | 潜能 2 |
| 0、4、3 白，2 黄 | 庄方宜、祀 | 潜能 3 |
| 0、4、3、2 白，1 黄 | 管理员 | 潜能 4 |
| 5 笔全白 | 全部 4★、5★，以及艾尔黛拉 | 满潜能 5 |

即：白色是已解锁的潜能，黄色是下一级，按固定顺序解锁，全白为满潜能。**这是从截图推断的，需要和游戏内的潜能对照确认。**

识别时只依赖黄色那一笔的位置：黄色饱和度高，在任何背景上都好认；白色笔画在浅色立绘上会看不清，只用来核对（30 张卡片里读到的白色笔画全部符合上表，没有一张矛盾）。

## 在浏览器里的流程

1. 解码（canvas；面积超过 1600 万像素时按比例缩小，iOS 的 canvas 上限）；
2. Web Worker 里找卡片、读潜能、裁出名字（`pipeline.ts`、`recognize.worker.ts`），长截图不卡页面；
3. Tesseract.js 认字（`ocr.ts`）：引擎和中文模型由本站提供（构建时从 npm 包复制到 `/ocr/<版本>/`，路径带版本号，长期缓存），
   不请求外部 CDN，符合 CSP（`script-src 'self' 'wasm-unsafe-eval'`、`worker-src 'self'`）。第一次下载压缩后约 3 MB，
   之后从浏览器缓存读取；
4. 候选名字用 canvas 画出来（本站的 MiSans 字体），Web Worker 里认名字（`identify.ts`）。

Chromium 实测（原图，生产构建 + 线上 CSP）：终末地 30/30（潜能 30/30），约 2.6 秒；明日方舟 56/56，没有需要确认的，约 6 秒
（其中比对 434 个候选名字约 2.5 秒）。第二次识别不用再加载 OCR，分别约 1.7 秒、4.5 秒。

## 鲁棒性测试

把两张截图做各种变形，再和原图上的结果比对（“标为请确认”：结果附带 low，界面上应该请用户核对；“没标出的错误”：错了但标为 high）。

终末地：

| 变形 | 卡片 | 星级 | 潜能 | 名字 | 潜能标为请确认 | 没标出的错误 |
|---|---|---|---|---|---|---|
| 原图 | 30/30 | 30/30 | 30/30 | 29/30 | 0 | 0 |
| 缩小到 0.75 | 30/30 | 30/30 | 30/30 | 29/30 | 1 | 0 |
| 缩小到 0.5（卡片 64 像素） | 30/30 | 28/30 | 26/30 | 21/30 | 30（太小，全部请确认） | 0 |
| 放大到 1080 / 1440 宽 | 30/30 | 30/30 | 30/30 | 29/30 | 0–1 | 0 |
| JPEG 质量 40 / 20 | 30/30 | 30/30 | 27/30 | 27–29/30 | 3–6 | 0 |
| 截掉顶部 / 只留中间 | 26/26、12/12 | 全对 | 全对 | 24/26、12/12 | 0 | 0 |
| 变暗 0.8 / 降低饱和度 0.7 / gamma 1.8 | 30/30 | 30/30 | 30/30 | 28–29/30 | 0 | 0 |
| 变亮 1.15（页面背景变成和名字栏一样白） | 29/30 | 23/29 | 23/29 | 22/29 | 6 | 0 |

明日方舟（星级，逐个星位判断；卡片只有 56 像素宽，按规则全部标为请确认）：原图 56/56，缩小 0.75 56/56、0.5 53/56，JPEG 质量 40 55/56、20 43/56，变暗、变亮、降低饱和度、gamma 都是 56/56。

做到这些靠的是：
- 颜色用相对的分数，而不是固定门槛：黄色那一笔只要“明显比其他四笔都黄”，白色笔画只要“比一侧背景亮”；
- 压缩把黄色洗掉时，改用“亮的笔画正好是解锁顺序的前几笔”推断，并标为请确认；
- 每张卡片用名字栏上沿重新对齐（长截图拼接造成的行距误差）；找不到时扩大范围；
- 卡片宽度低于 90 像素时，潜能和星级一律标为请确认。

还没覆盖的：明日方舟 5★ 以下（逐个星位判断时，立绘的黄色紧挨着最后一颗星可能多数一颗，会和长度核对不一致而标为请确认）、深色主题、横屏 / 平板的列数、截图里混入弹窗或滚动条。

## OCR 的选择

- Tesseract.js：核心 WASM 约 3 MB，简体中文模型 `chi_sim`（4.0.0_best_int）约 1.7 MB（gzip）。每张名字图约 25–40 ms。只在用户打开识别功能时加载。
- 名字是已知集合，OCR 认错一两个字也能纠正，所以不需要更重的模型。如果原图上的准确率仍然不够，再考虑 PaddleOCR（onnxruntime-web）。
